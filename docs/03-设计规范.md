# 03 · 设计规范（改动标准）

## 一、改动粒度

- **一个需求 = 一个"节 + 键"的改动**。宁可分多次部署，不要一次堆几十项。
- 每次部署的改动上限建议 ≤ 20 项；超过要拆分并分别留日志。
- 同一批改动里不要混入"顺手优化"——没点名的一律不动。

## 二、数值上下限（写入前校验，越界直接拒绝）

| 字段 | 允许范围 | 备注 |
|---|---|---|
| `Strength`（血量） | 1 – 100000 | 整数 |
| `Cost`（造价） | 0 – 100000 | 通常 50 的倍数 |
| `Speed` | 1 – 100 | 步兵 4-8、载具 4-10、飞行器 20-40 为常态区间 |
| `Sight` | 1 – 20 | |
| `TechLevel` | -1 – 15 | `-1` = 不可建造 |
| `Damage` | -10000 – 100000 | 负值为治疗类 |
| `ROF` | 0 – 1000 | 单位是**帧**，30 帧 ≈ 1 秒 |
| `Range` | 0 – 100 | 单位是**格** |
| `Burst` | 1 – 20 | |

> 超出范围的改动必须由用户明确确认，并在 devlog 记录理由。

## 三、写入格式要求

1. **只改值，不动行结构**：`Key=Value` 的 key 原样保留（含大小写与等号两侧空格）。
2. **保留换行符**：原文件是 CRLF，不得改成 LF。
3. **不凭空加 BOM**：原文件无 BOM 就不加（MO 自身文件带 BOM，但我们以抽出的基准为准）。
4. **不重排、不合并、不删注释**：所有 `;` 注释原样保留。
5. **同节同名键只改第一次出现**（RA2 解析器取首个）。
6. **不新增键**——`ini_edit.py` 会在键不存在时报错并整批回滚，这是有意设计。

## 四、命名规范

| 对象 | 规范 | 例子 |
|---|---|---|
| 覆盖文件 | 固定 `rulesmo.ini` | — |
| 改动清单 | `changes/<批次名>.json` | `changes/2026-11-11-batch1.json` |
| 部署快照 | `backup/<时间戳>/`，含 `rulesmo.ini` + `sha1_manifest.txt` | `backup/20261111_1530/` |
| 日志 | `devlog/YYYY-MM-DD.md` | `devlog/2026-11-11.md` |

改动清单 JSON 格式：

```json
{
  "batch": "2026-11-11-batch1",
  "note": "用户 R-001 ~ R-003",
  "changes": [
    {"section": "APOC", "key": "Strength", "value": 500},
    {"section": "COMA", "key": "Cost", "value": 1000}
  ]
}
```

## 五、复核标准（缺一不可）

1. `ini_compare.py` 差异条数 **==** `changes[].length`。
2. 差异内容与清单逐条对得上（节名、键名、新值）。
3. `sha1` 前后不同。
4. 文件大小变化 == 各条新旧值长度差的代数和。

## 六、部署前必查

- [ ] 游戏进程未运行（`gamemd.exe` / `MentalOmegaClient.exe`）
- [ ] 已有 `rulesmo.ini` 的话先做快照 + sha1
- [ ] 改动条数与名单一致
- [ ] 目标单位确认是**玩家版** ID（不是 AI 版）
